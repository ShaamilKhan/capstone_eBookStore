Section 01

System Architecture

Three-tier architecture: a React frontend talks to a Spring Boot REST API, which persists all data to PostgreSQL via JPA and Flyway.

Key Design Decisions

Stateless JWT — no server-side session Vite proxy — no CORS issues in dev Flyway — versioned DB migrations Spring Security filter chain H2 in-memory DB for tests only

Frontend to Backend Communication

All API calls use Axios with base URL /api. Vite's dev proxy forwards every /api/* request to http://127.0.0.1:8080. The JWT token is automatically attached from localStorage via an Axios request interceptor on every call.

Flyway Migration Files

V1__init_schema.sql — creates all 8 tables V2__seed_data.sql — 12 books, 4 categories, 3 publishers V3__book_images.sql — cover image URLs from Open Library

Flyway tracks every migration in a flyway_schema_history table. On every app startup it checks checksums — if a file changed it refuses to start, preventing silent schema drift in production.

Section 03

How Authentication Works

The app uses stateless JWT (JSON Web Token) via Spring Security. No sessions are stored server-side — every request proves its identity by carrying a signed token in the HTTP header.

Step-by-Step Login Flow

1
User submits credentials
Frontend sends POST /api/auth/login with email + password (plain text, encrypted in transit).
↓
2
BCrypt password verification
Spring's BCryptPasswordEncoder compares the submitted password against the stored hash. Plain text password is never stored.
↓
3
JWT token generated and returned
JwtUtil.generateToken() creates a token with the user's email as subject, signed with HMAC-SHA-512, expiry 24 hours. Returned to the browser.
↓
4
Token stored in localStorage
Frontend stores the JWT. An Axios interceptor attaches it automatically as Authorization: Bearer <token> on every subsequent request.
↓
5
JwtAuthenticationFilter validates every request
Before any controller runs, the filter reads the token, verifies the signature, checks expiry, loads the user, and sets the Spring SecurityContext. If invalid — request is rejected with 401.
// JwtAuthenticationFilter — runs on every HTTP request @Override protected void doFilterInternal(request, response, chain) { String header = request.getHeader("Authorization"); if (header == null || !header.startsWith("Bearer ")) { chain.doFilter(request, response); // no token — pass through return; } String jwt = header.substring(7); String email = jwtUtil.extractUsername(jwt); // verify signature UserDetails user = userDetailsService.loadUserByUsername(email); if (jwtUtil.isTokenValid(jwt, user)) { SecurityContextHolder.getContext() .setAuthentication(new UsernamePasswordAuthenticationToken(...)); } chain.doFilter(request, response); }

Section 04

API and Controller Flow

Every feature follows the same Controller → Service → Repository pattern. The controller handles HTTP, the service owns business logic, the repository talks to PostgreSQL via Spring Data JPA.

Example: Browse Products Request

1
Browser sends GET request
GET /api/products?categoryId=2&sort=price_asc&page=0&size=12
↓
2
Spring Security validates (public route — passes through)
No token needed for product browsing. Filter passes the request straight to the controller.
↓
3
ProductController receives request
Spring MVC binds query params. Calls productService.getProducts(categoryId, sort, page, size).
↓
4
ProductService builds a JPA Specification
Dynamic filters (category, brand, search, price range) are combined into a Specification. Passed to the repository with a Pageable (page + sort).
↓
5
Repository queries PostgreSQL
Hibernate translates the Specification into SQL: SELECT * FROM products WHERE category_id=2 ORDER BY price ASC LIMIT 12 OFFSET 0
↓
6
DTO mapped and returned as JSON
Entities are mapped to ProductSummaryResponse records — no internal fields exposed. Response: { content: [...], totalElements: 12, totalPages: 1 }
